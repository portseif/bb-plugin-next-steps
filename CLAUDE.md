Guidance for Claude Code (claude.ai/code) when working in this repository.

## Project Overview

**Next Steps** is a BB plugin that shows AI-suggested next steps for the current
project in a bare banner above an empty composer. Suggestions are produced by
spawning a hidden analysis thread inside the project, so they are grounded in the
real repository and generated by the user's own provider.

- Plugin id: `next-steps` — manifest name "Next Steps", icon `ListTodo`
- `engines.bb`: `>=0.35` · `engines.bbPluginSdk`: `^0.4.1`
- Installed from this path (`bb plugin install .`), not from git or npm
- Git repo on `main`, clean, remote `https://github.com/portseif/bb-plugin-next-steps`
- `bb.skills` is `[]` — this plugin ships no agent skills on purpose

## Architecture

```
server.ts            backend — generation lifecycle, kv cache, rpc, bb next-steps CLI
lib/suggestions.ts   pure prompt construction, parsing, dedupe, ranking (no bb API)
app.tsx              frontend — the composer banner
components/ui/       vendored shadcn source — yours to edit, never updates on its own
```

`lib/suggestions.ts` has no plugin API access so all of it is unit-testable without a
running BB. Keep `bb.*` in `server.ts`.

## How generation works

1. The banner calls `suggestions`. If nothing is in flight, the server fires a
   background `requestGeneration` and returns immediately — the composer never waits.
2. `requestGeneration` spawns a **hidden** thread (`visibility: "hidden"`,
   `permissionMode: "auto"`, title "Next steps analysis") in the project, with the
   prompt from `buildAnalysisPrompt`.
3. `bb.events.on("thread.idle")` catches that thread finishing, parses its last
   assistant message, caches the result, and archives the thread.
4. `thread.idle` on any *other* thread is what triggers the next refresh — a thread
   finishing is the moment the project's next steps actually change.

The analysis prompt is explicitly read-only and cheap: no writes, no state-changing
commands, no test suite, no build, no subagents or workflows. Keep it that way; this
runs in the background on the user's own provider quota.

## Guard rails that must not be weakened

- **The cooldown is keyed on the last *attempt*, not the last success**
  (`attempt:<projectId>`). A run that fails or returns unparseable output must not be
  retried on the next rpc call, or an empty result becomes an infinite spawn loop.
- **Two locks, on purpose.** The kv `inflight:` row is async, so two composers
  mounting at once can both pass it. The synchronous `spawning` Set is the companion
  that actually prevents a double spawn.
- **`INFLIGHT_TIMEOUT_MS` (10 min)** abandons a generation that never reports back.
- **`state: "generating"` only when a run is genuinely in flight.** A stale cache
  sitting inside its cooldown is not progress and must not report as such.
- **`thread.originPluginId === bb.pluginId` is skipped** on idle, so the plugin never
  reacts to its own threads.

## Suggestion bookkeeping (kv keys, all per project)

| Key | Holds |
|---|---|
| `cache:<projectId>` | The cached `SuggestionCache` |
| `inflight:<projectId>` | `{ threadId, startedAtMs }` of the running analysis |
| `analysis:<threadId>` | Reverse lookup: analysis thread → project |
| `attempt:<projectId>` | Last spawn attempt ms — the cooldown |
| `used:<projectId>` | Comparison keys of suggestions already used (cap 60) |
| `recent:<projectId>` | Verbatim recent proposals fed back as "don't repeat these" (cap 12) |

The analysis is asked for `count + CANDIDATE_SURPLUS` (3) suggestions. The surplus is
what lets `rankByNovelty` drop repeats without leaving the list short when the repo
genuinely has the same top priorities as last time.

`suggestionKey()` is deliberately loose — lowercased, punctuation and emphasis
stripped — because wording drifts between runs and a reworded repeat is still a
repeat. Used suggestions are filtered on *read*, not deleted from the cache.

## Frontend

`app.tsx` registers a composer customization (`app.composer.customize`) with one
banner: id `suggestions`, `chrome: "bare"`, scopes `thread`, `new-thread`,
`side-chat`. Project resolution differs per scope — `new-thread` and `side-chat`
carry their own `projectId`, everything else falls back to `useBbContext()`.

Keys: `→` drops the highlighted suggestion into the composer, `↑`/`↓` cycle, `Esc`
hides the banner for now. Arrow keys are only claimed while the caret sits in an
empty composer (`isComposerFocused`) — anywhere else they belong to the host.

Settings are read as `values?.x !== false` because `values` is `undefined` while
settings load and the correct answer in that window is the default.

## CLI

```sh
bb next-steps show    [--project <proj_id>]   # print cached suggestions + age
bb next-steps refresh [--project <proj_id>]   # force a run now
bb next-steps clear   [--project <proj_id>]   # drop the cache and the cooldown
bb next-steps forget  [--project <proj_id>]   # forget used + recently proposed
```

`--project` defaults to the project in CLI context; without either, the command
exits 1. `clear` is the fast way to unstick a bad cache; `forget` is the way to let
previously used suggestions come back.

## Settings

| Setting | Type | Default |
|---|---|---|
| `suggestionCount` | select 1–5 | `3` |
| `refreshMinutes` | string | `10` |
| `autoDisplay` | boolean | `true` |
| `autoGenerate` | boolean | `true` |
| `refreshOnThreadIdle` | boolean | `true` |
| `arrowCycling` | boolean | `true` |

With `autoDisplay` off the list stays behind a button and nothing is fetched or
generated until the developer asks.

## Development

```sh
npm install                   # once, before any build
npx tsc --noEmit              # typecheck — currently clean
bb plugin build               # dist/server.js + app.js/app.css + *.meta.json
bb plugin reload next-steps   # after editing sources
bb plugin dev                 # watch + hot reload the frontend
bb plugin logs next-steps     # where every generation failure is logged
```

React and the BB-shimmed packages are provided by the host at runtime and never
bundled.

`types/*.d.ts` are a vendored copy of the BB plugin API, mapped by `tsconfig.json`
paths. Refresh with `bb plugin types` (or `--check` in CI) after a BB upgrade;
`bb plugin build` and `bb plugin dev` refresh them for you.
